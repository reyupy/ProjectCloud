# Анализ логов Cloud.ru — этап 1

Локальный Python CLI для первичного разбора ошибок OpenSearch. Программа читает
логи, группирует повторения и подготавливает цепочки запросов для инженера и
будущей LLM. GigaChat, автоматическое исправление серверов и метрики
Prometheus/Grafana на этом этапе не подключены. На сервере логи не изменяются.

## Подготовка

Нужны Python 3.11+, сетевой доступ к OpenSearch (для лабы — VPN) и права чтения.
Из папки репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
Copy-Item .env.example .env
```

Укажите адрес и при необходимости учётные данные в `.env`. Переменные окружения
имеют приоритет над файлом. Файл читается как буквальные `KEY=value`, без запуска
команд и подстановки переменных. Пароль, `.env`, базу состояния и отчёты не нужно
добавлять в Git. Используйте HTTPS при доступе за пределами доверенной сети;
проверка сертификатов включена.

## Запуск

Разовый разбор окна `[start, end)` с обязательным часовым поясом:

```powershell
python -m cloudru_monitor analyze --start 2026-11-15T09:00:00+03:00 --end 2026-11-15T10:00:00+03:00 --output .local/report.json
```

`--replay` включает ранее обработанные ошибки и обходит кеш. Для другого
эксперимента можно использовать отдельный `--state .local/experiment.sqlite3`.
Ручной `analyze` отмечает успешно обработанные события для разовых запусков.
`watch` подтверждает обработку после собственного прохода зрелого окна.
`--replay` обходит отметки об обработке и оставляет прогресс прежним.
Без `--output` JSON выводится в stdout, диагностика идёт в stderr.

Периодический запуск с 15-минутным начальным окном и минутным перекрытием.

```powershell
python -m cloudru_monitor watch --interval 60 --lookback 900 --overlap 60 --output .local/latest.json
python -m cloudru_monitor watch --once --output .local/latest.json
```

Окно заканчивается за `--lateness-seconds` плюс `--chain-padding-seconds` до
текущего времени. По умолчанию это 5 минут на доставку плюс 5 минут на связанные
события после ошибки. Начало первого окна хранится в SQLite до завершения прохода.
При отставании источника `watch` ставит обработку на паузу, сохраняя границу для
повторного прохода. После восстановления `--max-window-seconds` ограничивает
продвижение за одну итерацию (по умолчанию 3600 секунд).
После временного сбоя чтения непрерывный `watch` повторяет проход с сохранённой
границы. Слишком большое окно делится на меньшие интервалы с сохранением
перекрытия. Если даже интервал около секунды превышает лимит, CLI выводит
диагностику и завершает проход с кодом 2.

При `--output .local/latest.json` каждый проход атомарно обновляет этот файл.
Подтверждённые проходы с группами также сохраняются по `run_id` в
`.local/latest.json.history/`. Предыдущие цепочки остаются доступны после
пустого прохода. С общей базой состояния записи отчётов сериализуются.
Если все ERROR прочитаны, проход с пустой или усечённой цепочкой может записать
частичный отчёт и продвинуть контрольную точку. Это требует файлового отчёта
с историей и отмечается полем `watch_partial_chains`. Неполную цепочку можно
пересобрать разовым анализом. Временный сбой поиска цепочки оставляет границу
для повтора.
При сбое между доставкой файла и подтверждением SQLite возможна повторная выдача.
Остановка выполняется через Ctrl+C. Код выхода `watch --once` или `analyze` равен
0 для завершённого прохода, 2 при паузе или неполном результате, 1 при ошибке запуска.

## Алгоритм и границы

1. Проверить свежесть источника и отдельно измерить покрытие запрошенного окна.
   Записи с будущим timestamp исключаются из оценки свежести.
2. Прочитать сообщения-кандидаты `ERROR` с пагинацией; нормализовать уровни,
   поля приложения и идентификаторы запросов. На первом этапе отбор строго
   `ERROR`: уровни `CRITICAL` и `FATAL` отдельно не включаются.
3. Отбросить ранее обработанные записи по идентификатору документа в рамках
   конкретного источника; сгруппировать ошибки по сервису и шаблону сообщения.
4. Для группы сохранить количество, первое/последнее появление и примеры;
   выбрать представительную ошибку с идентификатором запроса, если он доступен.
5. Найти цепочку всех уровней по global request ID (или явно отмеченному local
   request ID), отсортировать по времени. Для global ID поиск охватывает окно
   анализа с отступом `--chain-padding-seconds`. Для local ID тот же отступ
   применяется к моменту представительной ошибки, и поиск ограничен её сервисом.
   По умолчанию отступ равен 300 секундам в каждую сторону.
6. Подготовить отчёт с хронологией и компактный контекст. Повторяющиеся шаблоны
   в контексте имеют количество, время первого и последнего появления и ссылку
   на исходный документ. Контекст включает представительный `ERROR` и раздельно
   группирует события до и после него. Сжимаются только соседние повторы.
   Полная хронология доступна в отчёте при усечении контекста.

Результат поиска описывает доступные записи в границах заданного окна.
Ошибки без request ID и ошибки с локальным ID без известного сервиса остаются
в отчёте с исходным доказательством и явным статусом. Похожие сообщения могут
относиться к разным причинам, группировка требует проверки инженером.
Для дополнительных полей задайте `OPENSEARCH_GLOBAL_REQUEST_ID_FIELDS` и
`OPENSEARCH_LOCAL_REQUEST_ID_FIELDS` списками через запятую.
Если часть индексов использует другое поле времени, перечислите дополнительные
поля типа date в `OPENSEARCH_TIMESTAMP_FALLBACK_FIELDS` в порядке приоритета.
Они используются для записей без предыдущих полей списка.
Поиск кандидатов зависит от индексируемых полей и поддержки regexp для
нестандартных keyword-форматов.

Старый источник помечается как `stale`; отсутствие свежих записей не означает
отсутствия ошибок в работающей системе. Пределы ошибок/цепочек и число групп
ограничены; усечение и проблемы чтения показываются явно. Неполный отбор ERROR
сохраняет контрольную точку и оставляет записи доступными при следующем запуске.
Если окно превышает лимиты, уменьшите `--max-window-seconds` в `watch` или разбейте
запрос `analyze` на меньшие окна. Лимиты задаются через `OPENSEARCH_MAX_ERRORS`,
`OPENSEARCH_MAX_CHAIN_EVENTS` и `--max-groups`. Ошибка записи отчёта оставляет
прогресс прежним.

SQLite хранит обработанные идентификаторы, контрольные точки и метаданные
запусков. Сырой поток туда не копируется. Необязательный TTL-кеш хранит JSON
отчёта с выбранными доказательствами; включается `--cache-ttl-seconds`, по
умолчанию выключен. `watch` проверяет окно через новое чтение источника.
Локальные отчёты, их история и кеш могут содержать конфиденциальные сообщения.
Задержка доставки сверх настроенного запаса и окна перекрытия требует
`analyze --replay` за соответствующий период. Максимальный timestamp отражает
наблюдаемое запаздывание всего источника. Предел задержки отдельных сервисов
задаётся настройкой и подтверждается на потоке лабы.

Версия алгоритма и запросов изменяет ключ источника в SQLite. При обновлении
`watch` берёт начальное окно из `--lookback`. Для ранее пропущенного периода
используйте явное историческое окно или увеличьте начальный `--lookback`.

## Проверка

```powershell
python -m pytest
python -m cloudru_monitor --help
```

Тесты используют синтетические сообщения и имитацию HTTP, не требуют лабы или LLM.
